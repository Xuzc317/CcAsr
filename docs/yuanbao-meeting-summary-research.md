# 腾讯会议「元宝纪要 / 问元宝」会议总结功能调研

> 调研目标：搞清输出格式与结构化呈现方式，用于复刻产品形态（React + FastAPI）
>
> 调研时间：基于 2026-09 前后公开资料
> 证据分级：**【官方明说】** = 腾讯官方文档/官网原文　**【实测截图】** = 实际产品截图/录屏　**【推断】** = 我基于证据的合理推断

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 输出结构 | 有稳定模板：**基础信息（主题/发言人/摘要）→ 核心结论 → 按议题分章 → 待办事项 → 个人笔记**，且支持 6 套场景模板切换 |
| 图表能力 | 有，但**不是自由绘图**：AI 按内容逻辑**自动挑选固定组件**——分栏色块、三线表格、垂直时间轴、流程条（编号步骤网格）、共享画面截图 |
| 「线路」 | 存在，就是 **「流程条」**（01/02/03/04 编号步骤网格）+ **时间轴**；**没有**泳道图/决策路径图/话题流转连线图 |
| 技术路径 | **混合**：正文纪要 = LLM 输出 **Markdown**（官方 API 直接返回 Markdown）；「一张图看懂本场会议」= LLM 输出 **HTML**，前端有「代码/预览」切换 |
| 复刻建议 | **LLM 输出结构化 JSON → React 组件库渲染** 为主，Markdown 作为文本片段字段；Mermaid 仅作按需补充且必须兜底 |

## 1. 元宝会议总结的输出结构

### 1.1 产品入口与三个 Tab

腾讯会议「智能录制 / 录制详情页」的固定三 Tab 结构（官方帮助中心原文）：

```
录制详情页
├── 纪要     ← 会议总结主体
├── 时间轴   ← AI 按语义切分的章节时间轴
└── 逐字稿   ← 转写全文（按发言人分段 + 时间戳）
```

> **【官方明说】** 官方帮助中心《新版智能录制》：
> 「新版智能录制对**智能纪要、时间轴、逐字稿**等功能进行了升级」
> 「**纪要**：会议纪要模型全面升级……点击内容，一键跳转索引信息，**追踪会议决策过程**。」
> 「**时间轴**：完整回顾会议流程，生成结构清晰的时间轴。AI 根据语义智能切分讨论章节……并随时可以回到会议现场，回顾任一环节的完整上下文与**推演过程**。」
> 「**逐字稿**：……关键发言人观点可随时让 AI 总结，点击感兴趣的任何一句逐字稿，即刻定位到原文位置。」
> — https://meeting.tencent.com/support/topic/2228/index.html

### 1.2 「纪要」Tab 的板块层级（完整清单）

以默认的**「图文总结」模板**为例，【实测截图】还原出的层级：

```
纪要 Tab
├─ ① 会议主题（H1 标题）
│     例：「人形机器人竞争格局分析研讨会」
├─ ② 发言人 / 参会人（键值行 + 头像组）
│     例：「👥 刘丽婷、林浩、舒洁、大王、滴滴等 6 人」
├─ ③ 主题摘要（高亮段落块，左边框强调）
│     一整段话，概括本场会议背景与目的
├─ ④ 核心结论（高亮块 + 加粗标签 bullet）
│     • 「人形…」产业链……但同质化竞争与盈利压力已成为主要挑战。
│     • 2026 年将成为量产元年，未来竞争焦点将转向具身智能…
├─ ⑤ 正文：按议题分章（中文序号 H2：一、二、三…）
│     └─ 每个议题 = 一个小节标题 + 若干要点
│        ★ 小节的「呈现形态」由 AI 按内容逻辑自动决定（见第 2 节）
│        例：「产业链全景与核心布局」→ 分栏色块
│            「市场竞争格局与资本动态」→ 三线表格
│            「核心零部件发展时间线」→ 垂直时间轴
│            「培训议程设置」→ 流程条
├─ ⑥ 待办事项（**表格**：事项 | 责任人 | 截止时间）
│     例：整理渠道成本回报数据并向董事会汇报 | 刘丽婷、舒洁 | 下周内
│         准备新产品的媒体与公关策略提案       | 柏林（泊霖） | 下周会议前
│         细化新季度主推产品方案及相关材料     | 各部门负责人 | 下周内
└─ ⑦ 笔记（个人笔记，人工写入，独立置于最下方，不混入 AI 正文）
```

> **【官方明说】** 官方帮助中心《新版智能录制》对板块的描述完全对应：
> 「录制详情页-「纪要」中查看本场录制的**基础信息（主题、发言人、会议摘要）、会议纪要、待办事项**。」
> 「④ 点击纪要内容右上角…按钮，即可对当前播放节点**添加笔记备注**。完成添加后将按照添加时间呈现在纪要内容**底部「笔记」模块**。」
> 「⑤ 点击纪要内容左上角**「模板」**，即可根据需要**切换纪要模板**，切换后即可生成相应的纪要内容。」
> — https://meeting.tencent.com/support/topic/2228/index.html

### 1.3 六套纪要模板（同一场会，六种读法）

**【实测截图 + 第三方实测】** 模板下拉菜单实拍，共 6 个：

| 模板 | 组织结构 / 侧重点 | 证据 |
|---|---|---|
| **图文总结** | 默认。主题摘要 + 核心结论 + 自动图文混排（表格/分栏/时间轴/流程条/共享画面） | 【实测截图】 |
| **学习笔记** | 课程名称 / 发言人 / 课程简介 → **一、核心知识精讲**（知识要点）→ 重难点 → **AI 延伸思考**（AI 自己出思考题） | 【实测截图】 |
| **汇报总结** | **以汇报人为单位**组织：谁说了什么、进展、阻碍 | 【第三方实测】 |
| **项目启动纪要** | **背景目标 / 时间线 / 分工 / 风险 / 答疑** | 【第三方实测】 |
| **客户拜访纪要** | 按 **MEDDICC** 框架（指标、经济买家、决策标准、决策流程、痛点、内线、竞品） | 【第三方实测】 |
| **客户分析** | 按 **BANT** 框架（需求、预算、决策权、时间） | 【第三方实测】 |

> **【官方明说】** 官方事件回调 `smart.minutes` 中确有模板字段：
> `template_type`　纪要模板类型：`0：通用模板　1：自定义模板`
> — https://cloud.tencent.com/document/product/1095/121286

**「学习笔记」模板的实测层级**（可作为模板差异化的样例）：

```
课程名称：AI智能体与通用人工智能发展前景        ← 对标"会议主题"
发言人：说话人01、说话人02、说话人03、说话人06、说话人04等6人
课程简介：本课程深入探讨了……                   ← 对标"摘要"
一、核心知识精讲
   本次会议主要围绕……具体包括以下几个维度：
   1. AI智能体的发展现状与瓶颈                 ← 阿拉伯数字小节
      • 智能体发展时间线：说话人01认为……
      • 智能体的核心缺陷：目前的智能体缺乏……
      • 智能体的应用场景：智能体在代码编写等……
   2. 强化学习（RL）的局限性
      • RL 的监督信号稀缺性：……
```

> 规律：**加粗标签 + 中文冒号 + 内容** 是贯穿所有模板的要点句式。这是最容易复刻、也最影响观感的细节。

### 1.5 其他要素：可溯源时间戳 & 个人笔记

- **每一条纪要正文都挂可点击时间戳**，点击后右侧视频跳转到对应位置。
  > **【第三方实测】**「图文纪要里的所有文字内容都带时间戳。点击任意一条纪要，右上角的会议视频会自动跳到对应的时间点。」

- 纪要正文**全部可编辑**，双击可**自动保存为图片**便于转发。

这是本次调研最关键的发现。腾讯官方对外的原话是：

> **【官方明说】** 官方新闻《同事开会从不记笔记，怎么问什么都答得上来？》：
> 「会议结束后，元宝还能**生成图表**、提炼待办，并结合联网信息，把讨论成果沉淀为可复用的上下文资产。」
> 「问元宝设置了高频问题快捷入口：**一张图看懂本场会议、核心决策提取、会议待办生成**等等……」

## 3. 「线路」相关：确认结论

### ❌ 未找到可靠来源的形态

以下形态**在腾讯会议元宝纪要中均未找到任何可靠证据**（官方文档、官网新闻、实测截图、第三方评测均未出现）：

- **流程图 / 泳道图**（任务流转）——未找到
- **思维导图 / 树状图**（议题拆解）——纪要里**没有**。注：腾讯**元宝 App** 的「AI 深度搜索」有"一键生成脑图"能力，但那是元宝侧通用能力，**不是会议纪要的输出形态**
- **组织图 / 人物关系图**——未找到
- **甘特图**（排期）——未找到
- **决策路径图 / 话题流转连线图**——未找到。官方文案里的"**决策链条**"仅出现在销售场景的**问答用途**描述里（"销售可以用它来分析客户的决策链条"），**不是一个可视化图形**

> ⚠️ 特别注意：第三方文章里出现过「**表格与流程图等结构化数据天然对 Agent 更友好**」这句话，但那是作者对"结构化数据"的泛指论述，**上下文列举的实际组件是"表格、时间轴和流程条"**，不能据此认定产品里有流程图。

### 结论

元宝的"线路"= **流程条（编号步骤）+ 时间轴（含时序节点）**，都是**线性、单向、无分支**的表达。
**没有**任何**多分支、带判断节点、带角色泳道**的图形。这实际上降低了复刻难度。

### 4.5 关于"Markdown 还是 JSON"的最终判断

**混合路径，且分工清晰：**

| 层 | 载体 | 依据 |
|---|---|---|
| **正文纪要文本** | LLM 输出 **Markdown** | 官方 API `text_type=2` 直接返回 Markdown；问元宝"复制为 Markdown" |
| **视觉组件**（表格/分栏/时间轴/流程条） | **【推断】** LLM 输出"组件类型 + 数据"，前端用**固定组件库**渲染 | 证据：这些组件样式高度规整统一（配色固定、编号徽章固定、三线表固定），不像自由生成的 SVG/代码；官方文案用词是"**自动适配**……排版样式"，说明是"选择已有样式"而非"绘制图形" |
| **「一张图」** | LLM 输出 **受限 HTML**，前端预览渲染 | 官方明说 + 「代码/预览」Tab |
| **图片导出** | 前端截图（双击保存为图片 / 一键生成图片分享） | 官方帮助中心 + 官网新闻 |

**为什么要用 HTML 而不是 Mermaid —— 合理的工程解释：【推断】**
Mermaid/ECharts 需要严格语法 + 数据映射，LLM 容易出错；而 HTML+CSS 是模型见过最多的语料，`<div style="display:grid">` 天然表达"分栏色块""卡片网格"，容错性远高于 Mermaid。腾讯选择 HTML 是**牺牲可控性换取生成成功率**的务实选择。

## 5. 可复刻建议（React + FastAPI）

### 5.1 三方案对比

| 维度 | A. LLM → Mermaid → mermaid.js | B. LLM → JSON → ECharts/Recharts | C. 混合（推荐） |
|---|---|---|---|
| **适用图形** | 流程图、时序图、状态图、ER、甘特、思维导图 | 柱/线/饼/雷达等**统计图**；表格 | 全部 |
| **语义匹配度** | 高（本就是为流程图设计的） | **低**——ECharts 是**数据可视化**库，画不出"分栏色块""编号步骤卡" | 高 |
| **LLM 一次成功率** | 中低。节点数 >15、含中文标点（`（）""、`）、含换行标签时错误率显著上升 | **高**。JSON Schema 约束下基本不会语法错误 | 高 |
| **流式渲染** | 难。Mermaid 必须拿到完整代码才能 parse，流式输出时只能显示代码块 | 易。可分字段增量渲染 | 易 |
| **样式一致性** | 差。默认主题丑，需大量 CSS 覆盖，且版本升级易破坏 | **好**。完全由你控制 | 好 |
| **导出图片** | 需 `svg` → canvas，中文字体常出问题 | ECharts 自带 `getDataURL`；DOM 用 html-to-image | 好 |
| **失败模式** | 语法错误 → 整块白屏/报错；中文引号、括号、`end` 关键字冲突是高频雷区 | schema 校验失败需重试；数据为空时图表空白 | 局部降级 |

**关于 Mermaid 错误率的诚实说明：**
我**没有找到**任何权威的、可引用的"Mermaid 生成错误率"统计数据——腾讯官方也未公布。因此我不给具体百分比。**可以确认的是失败类别**：
1. 标签里含未转义的引号/括号/逗号 → parse error
2. 中文全角标点被解析为语法符号
3. 节点 ID 与保留字冲突（`end`、`graph`、`class`）
4. 节点数多时缩进/连线符号（`-->` vs `--`）不一致
5. 输出被 Markdown 代码块围栏截断（流式场景高发）

工程上应当**自己压测统计**：用你们的真实会议语料跑 200 场，统计 `mermaid.parse()` 失败率，再决定是否启用。

### 5.3 为什么这样选（理由）

1. **元宝的真实形态本来就是"固定组件库"**，不是自由绘图。上面 8 类组件用 React 写 8 个组件就覆盖了 95% 的场景，**根本不需要 Mermaid**。
2. **JSON Schema 约束（structured output / function calling）能拿到接近 100% 的语法合法率**，而 Mermaid 没有官方 schema，只能靠重试。
3. **`source_refs` 是可溯源体验的地基**。腾讯把"每条结论挂时间戳"当成核心卖点，这在 JSON 里是天然字段；在 Mermaid 代码里无处安放。
4. **流式体验**：JSON 可以边生成边渲染（先出 summary，再出 blocks），Mermaid 必须等完整代码。
5. **导出图片 / 二次利用**：结构化数据可以直接进 PPT、周报、Agent 调用（腾讯自己强调"结构化数据天然对 Agent 更友好"）；Mermaid 只能截图。
6. **可编辑**：腾讯纪要正文全部可编辑。结构化 block 可以做成"点击就地编辑"，Markdown/Mermaid 编辑体验差。

### 5.4 Mermaid 什么时候用

只在这两种情况引入，且**必须兜底**：

- **用户显式要求**："帮我画一张这个流程的流程图"（走问元宝式的对话入口，而不是纪要正文）
- **确实有分支/流转语义**且节点数 ≤ 12：审批流、状态机、任务依赖

**Mermaid 兜底策略（必须全做）：**

```ts
// 1. 先校验再渲染，失败不进 DOM
async function renderMermaid(code: string, host: HTMLElement) {
  try {
    await mermaid.parse(code);                    // 语法预检
    const { svg } = await mermaid.render(uid(), code);
    host.innerHTML = svg;
  } catch (e) {
    // 2. 一级兜底：自动清洗后重试一次
    const cleaned = sanitizeMermaid(code);        // 换全角标点、给含特殊字符的标签加引号
    try {
      await mermaid.parse(cleaned);
      const { svg } = await mermaid.render(uid(), cleaned);
      host.innerHTML = svg;
      return;
    } catch {}
    // 3. 二级兜底：回退到"结构化列表/表格"，绝不白屏
    host.innerHTML = renderFallbackOutline(code); // 把 flowchart 的节点+边渲染成缩进列表
    // 4. 三级兜底：展示原始代码 + 复制按钮
    showCodeBlock(code);
  }
}
```

配套措施：
- **后端二次修复**：把 parse error 回灌给 LLM 让它只修语法不改语义（一次重试，成本可控）
- **Prompt 侧约束**：强制节点 ID 用 `n1/n2`，标签一律加双引号，禁止在标签里用 `()` `""` `,`，节点数上限 15
- **离线兜底**：`mermaid.initialize({ securityLevel: 'strict', fontFamily: '...' })` 并预加载中文字体，否则导出 SVG 中文变方框
- **流式场景**：Mermaid 代码块在流式输出期间只显示代码，**检测到结束标记后才渲染**

### 5.5 「一张图」用 HTML 怎么做才安全

如果也要复刻"一张图看懂本场会议"（**强烈推荐复刻，这是记忆点最强的功能**）：

```tsx
// 后端：LLM 输出受限 HTML 子集，服务端白名单净化
// 用 bleach / DOMPurify(jsdom) 只放行：
//   div span h1-h4 p ul ol li table thead tbody tr th td strong em br hr
//   style 属性只放行：color background border display grid-template-columns gap padding margin font-weight text-align
// 禁止：script iframe object embed on* 事件 javascript: URL 外链 img（图片走你自己的代理）

// 前端：iframe + srcdoc + sandbox，彻底隔离
<iframe
  sandbox=""                       // 不给 allow-scripts
  srcDoc={sanitizedHtml}
  className="w-full min-h-[600px] rounded-xl bg-white"
/>
```

或者更可控的**降级方案**：让 LLM 直接输出上面 5.2 的 JSON（`type: "infographic"`），前端用 `<InfographicGrid/>` 组件 + 主题色映射渲染——**牺牲一点自由度，换取 100% 可控和可导出**。这其实是元宝"组件库"思路的更彻底版本，我更推荐这条。
